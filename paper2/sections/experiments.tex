\subsection{Experimental Setup}

\subsubsection{Test Set Construction}
\label{subsubsec:testset}

Our primary evaluation is based on 94 manually annotated test cases covering the three target domains (government affairs: 42 cases; finance: 28 cases; environment: 24 cases). This manually verified set is designed for controlled comparison between expert rules and generated rules rather than for estimating production-scale defect prevalence. Test case construction followed a three-step protocol:

\begin{enumerate}
    \item \textbf{Defect Injection.} Starting from verified clean KG triples extracted from official domain documents, we systematically introduced defects across all four rule types (Section~\ref{subsubsec:rule_def}): attribute omissions ($r_{\mathrm{attr}}$), inadmissible relations ($r_{\mathrm{rel}}$), out-of-range values ($r_{\mathrm{val}}$), and temporal/hierarchical ordering violations ($r_{\mathrm{ord}}$). Each defective case contains exactly one injected defect to enable unambiguous recall and defect-type analysis; clean counterparts are retained for false-positive checking.
    \item \textbf{Annotation.} Two domain experts independently labeled each case as defective or clean, along with the defect type. Inter-annotator agreement was $\kappa = 0.91$ (Cohen's $\kappa$). All 7 disagreement cases were resolved by a third expert through adjudication.
    \item \textbf{Coverage.} The 94 cases span 14 entity types and cover all four defect categories, with distribution: $r_{\mathrm{attr}}$ (31), $r_{\mathrm{rel}}$ (25), $r_{\mathrm{val}}$ (22), $r_{\mathrm{ord}}$ (16).
\end{enumerate}

\subsubsection{Rule Generation Evaluation}
We designed comparative experiments to evaluate two rule sets based on the 94 annotated test cases:
\begin{itemize}
    \item \textit{Expert Rule Group}: 37 basic quality rules from domain knowledge
    \item \textit{Generated Rule Group}: 294 rules automatically generated by our dual-strategy method
\end{itemize}

\subsubsection{Evaluation Metrics}
\begin{itemize}
    \item \textit{Precision}: Proportion of true quality problems among identified issues
    \item \textit{Recall}: Proportion of all known problems that rules can detect
    \item \textit{Coverage Score}: Breadth of potential problems rules can detect
    \item \textit{Unique Ability Score}: Capability to detect problems that expert rules cannot identify
\end{itemize}

\subsubsection{Ablation Study: RL vs. Fixed and Sequential Strategies}

To verify that performance gains stem from RL's adaptive decision-making rather than the action definitions themselves, we compare six strategies. Beyond the original four, we add two \emph{sequential} baselines that interleave the same action types but in a predetermined order:

\begin{itemize}
    \item \textbf{Rule-First-Then-Fix}: Spend the first 60\% of the budget (30 episodes) generating rules only, then switch to graph enhancement exclusively for the remaining 40\% (20 episodes).
    \item \textbf{Fix-First-Then-Rule}: Spend the first 60\% enhancing the graph, then switch to rule generation exclusively.
\end{itemize}

These baselines isolate the question: \emph{does the RL agent benefit from dynamic switching, or would any fixed ordering achieve similar results?} All strategies use the same DQN action set, reward function, and hyperparameters; only the action-selection policy differs. Each condition is run with 5 random seeds; we report mean $\pm$ std of final joint quality $Q(G)+\lambda Q_{\mathrm{online}}(R)$.

\begin{table}[t]
    \centering

    \label{tab:rl_ablation}
    \begin{tabular}{l c c c c}
    \toprule
    Strategy & Episodes to Conv. & Final Quality & Std & vs.\ Baseline \\
    \midrule
    Fixed Enhancement Only           & 80            & 76.2          & $\pm$1.3 & ---      \\
    Fixed Rule Generation Only       & 90            & 73.5          & $\pm$1.8 & $-$3.5\% \\
    Rule-First-Then-Fix              & 72            & 77.4          & $\pm$1.5 & $+$1.6\% \\
    Fix-First-Then-Rule              & 75            & 76.8          & $\pm$1.4 & $+$0.8\% \\
    Alternating (50-50)              & 65            & 78.9          & $\pm$1.1 & $+$3.5\% \\

\end{table}

\textbf{Key Insights:}
\begin{itemize}
    \item \textbf{RL outperforms all heuristics}, including the best sequential schedule (Rule-First-Then-Fix, 77.4), confirming that the benefit arises from learned adaptive switching rather than the action set alone.
    \item \textbf{Sequential strategies beat pure fixed strategies} (77.4/76.8 vs.\ 76.2/73.5), showing that \emph{some} ordering helps, but it is far from optimal without state-conditioned decisions.
    \item \textbf{Fix-First-Then-Rule is worse than Rule-First-Then-Fix} (76.8 vs.\ 77.4): enhancing the graph before having good rules yields less informative corrections, whereas building a rule base first guides more targeted graph fixes.
    \item \textbf{Fixed Rule Generation Only remains the worst} (73.5): rules alone without graph enhancement stagnate $Q(G)$.
    \item \textbf{RL has the lowest variance} ($\pm$0.9 vs.\ $\pm$1.1--1.8), indicating more consistent convergence across seeds.
    \item Statistical significance vs.\ best heuristic (Rule-First-Then-Fix): $p < 0.01$ via paired t-test across seeds.
\end{itemize}

\subsection{Comparison with Rule Mining Baselines}%放到4.2

We compare against representative automatic rule-mining methods under the same manually verified evaluation protocol. Since AMIE and RuDiK primarily mine structural Horn rules from graph triples, they are given only the extracted KG triples as input and their outputs are mapped to the closest detectable defect types among relation validity, hierarchy, and structural consistency. Neural rule learning is evaluated under the same input setting. These baselines do not receive the original source text, prompt context, or LLM-generated textual variants, so they are disadvantaged on source-text-dependent attribute, value, and procedural constraints. This comparison therefore tests whether graph-structure-only rule mining can recover the quality rules needed by our task, rather than claiming that all methods have identical information access or identical supervision.

\subsection{External Benchmark Platform}
\label{subsec:external_benchmark}

To test whether the quality-enhancement pipeline behaves robustly outside the three in-domain regulatory datasets, we built a local end-to-end benchmark platform using two existing benchmark-style resources in the repository. First, we use a TNEWS/CLUE-style Chinese news dataset as an out-of-domain text source. A deterministic extractor constructs a document--category--entity KG from 3,000 balanced news titles across 15 categories; we then inject duplicate triples, invalid relations, and isolated nodes, and run the local repair pipeline. Second, we use the 94-case rule-test set as a labeled rule-detection benchmark. This benchmark is fully local and makes no LLM/API calls, so it evaluates KG quality control and rule execution rather than LLM extraction quality.

\subsection{Failure Case Analysis and Limitations}
% 在某一方面的能力上的缺陷，分类
While our system achieves promising performance, we identify several failure cases that reveal current limitations:

\subsubsection{Failure Case 1: Domain-Specific Terminology}

\textbf{Example:} In the finance domain, the system generated a rule "regulatory penalties must specify violation amount" but failed to detect term confusion (e.g., mistaking an unrelated phrase for the correct regulatory-subject term) in 3 out of 15 instances.

\textbf{Analysis:}
\begin{itemize}
    \item Qwen-32B's training data may lack sufficient domain-specific financial terminology in Chinese
    \item The deletion completion strategy masked entities but not terminology errors
    \item The augmentation strategy generated variations but preserved the incorrect term
\end{itemize}

\textbf{Implication:} Domain-specific fine-tuning or expert lexicons are needed for specialized terminology. Future work should integrate domain glossaries into the masking and validation process.

\subsubsection{Failure Case 2: Complex Temporal Reasoning}

\textbf{Example:} The system failed to generate a rule detecting temporal inconsistencies where approval dates preceded application dates by 2+ days.

\textbf{Analysis:}
\begin{itemize}
    \item Neither deletion nor augmentation strategy explicitly models temporal constraints
    \item LLM-generated augmentations preserved temporal relationships from original text
    \item Rule extraction focused on entity types and relationships, not temporal logic
\end{itemize}

\textbf{Implication:} Explicit temporal reasoning modules should be integrated. Future work should add temporal constraint templates (e.g., "Event A must precede Event B") to the rule generation process.

\subsubsection{Failure Case 3: Low-Frequency Edge Cases}

\textbf{Example:} The system missed a rule about "penalty appeals must be filed within 60 days" because only 2 out of 94 test cases involved appeals.

\textbf{Analysis:}
\begin{itemize}
    \item Frequency threshold ($\theta_{\text{freq}} = 0.7$) filtered out low-frequency patterns
    \item Augmentation strategy generated only 5 variations per text, insufficient to explore rare cases
    \item Test set of 94 cases may not cover all edge cases
\end{itemize}

\textbf{Implication:} Adaptive frequency thresholds based on pattern importance, or targeted augmentation for rare patterns, could improve coverage of edge cases.

\subsubsection{Quantitative Failure Analysis}

Beyond the 94-case primary test set, we additionally inspected 150 undetected defects sampled from development runs across all three domains. This auxiliary pool is used only for qualitative failure categorization and is not included in the main precision/recall tables:
\begin{itemize}
    \item 38\% (57 cases): Domain-specific terminology not in LLM knowledge
    \item 31\% (47 cases): Complex temporal or numerical reasoning
    \item 22\% (33 cases): Low-frequency edge cases (< 3 occurrences in training)
    \item 9\% (13 cases): Ambiguous rules requiring human judgment
\end{itemize}

\textbf{Limitations Summary:}
\begin{enumerate}
    \item \textbf{LLM Dependency:} System performance is bounded by Qwen-32B's capabilities and training data coverage
    \item \textbf{Computational Cost:} Rule generation requires \$120 per domain in API costs, limiting scalability
    \item \textbf{Test Set Size:} 94 test cases may not fully represent all quality issues in production KGs
    \item \textbf{Temporal Reasoning:} Current approach lacks explicit temporal constraint modeling
    \item \textbf{Hallucination Risk:} While we observe 100\% precision on the manually verified test set, LLM-generated rules may hallucinate in unseen domains
\end{enumerate}
